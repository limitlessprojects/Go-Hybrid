# RESULTS — ISSUE #4634 wildcard spike

**English one-liner.** A plain standard-library Go library binds mesh identity, enforces the
weight/overlap identity, exactly-once writes and the conservation law, and refuses a wrong-mesh
composition *before* any write, at the same caller effort as the compiler feature would have.
The proposal's drop condition holds for the constraints — with two honest qualifiers about API
shape (§7).

本文所有数字均来自本机实测，原始输出在 `logs/`（`python-model.txt`、`go-test.txt`、
`bench-run1..3.txt`）。没有跑过的内容在 §8「没做什么」里逐条列出，不作推测。

## 1. 预先声明的假设与证伪条件

以下三条在写第一行 Go 代码之前就已固定，是本 spike 的判定框架；§6 记录了实验中途我自己的
错误假设是怎么被推翻的（属于事后观察，单独标注）。

### H1 — 网格身份可以由普通 Go 库绑定，且几乎零成本

**主张**：把两侧网格的身份（边序列的指纹）放进一个不透明的 `Plan` 里，在每次调用入口做一次
检查，就能让「用 A→B 的 plan 去写 C 的场」在**任何一次写入之前**被拒绝；调用方不需要额外参数
（源/目标网格本来就要传），运行时成本不超过一次 apply 的量级。

**证伪条件（任一条成立即证伪）**：
- (a) 任一 API 在网格不匹配时返回 nil；
- (b) 拒绝之前已经写了目标场的任何单元（部分写入）；
- (c) 调用方为通过检查必须付出额外成本（额外参数、手工指纹、包装类型）；
- (d) 检查的运行时成本 ≥ 一次 apply，或带来额外分配。

### H2 — 两种调用形状都能在合法搬运上保持逐单元真值，且三条约束可由库强制

**主张**：回调式（库把目标下标交给调用方）与生成循环式（只暴露本 worker 拥有的目标行）在
issue 的全部合法搬运上逐单元等于独立 oracle；且「权重×目标宽度 == 重叠长度」「每目标单元
只写一次」「守恒律」三条约束都不需要编译器特性，普通库即可强制。

**证伪条件**：
- (a) 1536 个 mesh/data 例、4608 个调度布局里出现任何一次单元不一致；
- (b) 存在某条约束，库无法在运行期强制（例如写分区需要语言层面保证）。

### H3 — 组合场景是库 API 会静默接受错误网格的地方

**主张（运行前预测）**：把两次搬运串起来、故意用 A→B 的 plan 去写 C 的场（三个网格单元数相同，
所以下标检查无法发现），**绑定身份的 API 会拒绝，而未绑定的下标式实现会接受并写出错的场**；
如果连未绑定实现也拒绝，说明这个陷阱不存在，H3 被证伪。

**证伪条件**：
- (a) 绑定身份的 API 接受了错误网格 → 直接违反 issue 的判定基础；
- (b) 未绑定控制也拒绝 → 陷阱不存在，"绑定身份"没有买到任何东西。

## 2. Python 参考模型：独立复跑作者的数字

`python/model.py` 是照 issue 的**主张**重写的（sparse plan、两个 oracle、N1–N5 控制），不是
对 issue 代码块的转录。关键差异：plan 存成稀疏行（只存非零重叠）；oracle 用两个独立实现并互相
交叉验证——OBS-A 解析积分（把分段常数场的累积积分在目标边上取值，**完全不计算重叠长度**），
OBS-B 作者的单位栅格。

| 量 | issue 声称 | 本次复跑 | 判定 |
| --- | --- | --- | --- |
| 网格数（[0,4] 整数内点划分） | 隐含 8 | 8 | 一致 |
| 网格对 | 64 | 64 | 一致 |
| mesh/data 例 | 1,536 | **1,536** | 一致 |
| 调度布局（workers ∈ {1,2,3}） | 4,608 | **4,608** | 一致 |
| oracle 分歧（A vs B） | —（未报） | **0** | 两个独立 oracle 完全一致 |
| plan 与 oracle 分歧 | 0 | **0** | 一致 |

计数不是猜的：`3^cells` 在 8 个网格上求和 = 3+27+81+81 = 192，再乘 8 个目标网格 = 1536；
乘 3 种 worker 数 = 4608。模型里用断言而不是打印来固定这个数。

负数控制（全部按 issue 的叙述成立）：

| 控制 | 构造 | 结果 |
| --- | --- | --- |
| N1 交换等宽行 | mesh (0,1,2)，行互换，ρ=[1,4] | 积分 5 → 5 **守恒**，逐单元 [4,1] vs oracle [1,4] **错**，plan 被 `weight*width 0 != overlap 1` 拒绝 |
| N2 按下标拷贝 | (0,1,3)→(0,2,3)，ρ=[4,1] | 写调度 [0,1] **完全不重叠**，积分 **6 → 9**，plan 被 `weight*width 2 != overlap 1` 拒绝；正确的重叠加权给 [5/2, 1]，积分 6 |
| N3 行内搬权重 | 行 [1/2,1/2] → [1/4,3/4]，行覆盖仍 = 目标宽度 2 | 写分区看起来合法，逐条几何检查拒绝（`weight*width 1/2 != overlap 1`），积分 6 → 9/2 |
| N4 边距唯一性 | 枚举 64 个网格对的重叠二分图 | 64/64 是**森林**（无环、边数 = 节点数 − 连通块数）→ 1D 同域下 行边距+列边距 唯一确定权重，不存在"保持总和的补偿扰动" |
| N5 重叠声明 | 两个 worker 都声明第 0 行 | 检出 `row 0 written twice` |

N2 是 issue 的核心论点，复跑完全对上：**按单元下标搬运既保持长度又给出不重叠的写调度，积分却从 6 变 9**。N1 是第二个论点：**只看总和会漏掉"两个值都放错位置"**。

## 3. Go 主实验：两种 API 在合法搬运上的逐单元对照

`go-control/xfer` 是标准库模块（`math/big.Rat` 精确权重，`go.mod` 里 `go 1.22`）。plan 构造后
必须通过 `Validate`（几何 + 写分区 + 守恒三条），失败则根本不返回。

- **API A（回调式）** `Run.ApplyRows(worker, workers, src, dst, srcVal, write func(dstIndex int, v *big.Rat) error)`
- **API B（生成循环式）** `Run.GatherRows(worker, workers, src, dst, srcVal, dstVal) (int, error)`，循环体只能通过 `RowView.Store` 写自己那一行，机器码层面没有可选的其它下标

穷举：8 个网格 × 8 个目标 × {0,1,4}^源单元数 × workers{1,2,3}，两种 API 各自走一遍。
oracle 是 Go 里重写的解析积分，并与单位栅格 oracle 交叉校验。

```
xfer_test.go:159: plans=64 entries=208 cases=1536 layouts=4608 oracle_disagreements=0
xfer_test.go:204: cases=1536 layouts(workers=4)=1536
```

| 量 | 结果 |
| --- | --- |
| plan 数（有序网格对） | 64 |
| plan 条目总数（稀疏重叠项） | 208 |
| mesh/data 例 | **1,536** |
| 布局（workers 1,2,3；两 API 各跑一次） | **4,608** |
| 与解析 oracle 的单元分歧 | **0** |
| 两个 oracle 之间的分歧 | **0** |
| 守恒律 `∫dst == ∫src` 违例 | 0 |
| 每布局的写入记账 | 写入数 == 目标单元数，无重复声明（`Run.Finish` 通过） |
| workers=4（Python 模型没跑过的配置，单列） | 另 1,536 布局，分歧 0 |

| --- | --- | --- |

## 4. 组合实验：中间场身份搞错时，两个 API 接不接

三个 3 单元网格，同为 [0,4] 的划分、**单元数相同**，所以下标全部合法：

- `A [0,1][1,3][3,4]`（宽 1,2,1）
- `B [0,2][2,3][3,4]`（宽 2,1,1）
- `C [0,1][1,2][2,4]`（宽 1,1,2）

三者的指纹互不相同（`TestSameCellCountIsNotIdentity` 断言），所以**长度检查无法区分它们**。

| 场景 | 回调式 API A | 生成循环 API B | 未绑定控制 `ApplyUnbound` |
| --- | --- | --- | --- |
| `planAB` 写 C 的场（目标网格错） | **拒绝** `ErrMeshIdentity`，写 0 次 | **拒绝**，写 0 行 | **接受**，写出 `[5/2 1 9]` |
| `planAB` 读 C 的场（源网格错） | 拒绝 | 拒绝 | 不适用（无网格参数） |
| 源、目标同时错 | 拒绝 | 拒绝 | 不适用 |
| `planBC` 喂 A 的**裸 slice**（数值来自别的网格） | **接受**（见 §7 限制） | 接受 | 接受 |
| 同一个几何重建的 `Mesh`（值相同、指针不同） | 接受（身份是几何不是指针） | 接受 | 接受 |

最小复现（`TestMinimalReproWrongMesh` 原样输出）：

```
cells=3/3/3  plan_A->B.Apply(dst=C) -> xfer: plan is bound to a different mesh identity:
plan is A->B (fp 08a42f23cd3e78a7->a2a6a82692fda644), call names A->C
(fp 08a42f23cd3e78a7->b9a6195bba296066)
|  plan_A->B.ApplyUnbound(dst=C) -> <nil>, wrote [5/2 1 9]
```

同一份 plan、同样的三个数、同样的调用点：绑定身份的 API 在**写第一个值之前**就拒绝；未绑定的
实现写满了整个 C 的场、返回 nil，并且**写出来的每个数对 B 都是"正确"的**——这正是它危险的地方：

```
TestUnboundControlIsSilentlyWrong: unbound write into C: [5/2 1 9] (B's values [5/2 1 9],
C's true values [4 1 5]), integral check: <nil>
```

两个额外发现，都写进了测试：

1. **plan 作用域的守恒检查看不见这种替换**。`planAB.CheckIntegral` 用 plan 自己绑定的 **B 的边**
   去算目标积分，得到 15 == 15 通过；换成 C 的边就是 21.5 ≠ 15。也就是说：事后积分校验不能
   替代身份绑定，因为校验和 plan 相信的是同一张网格。
2. **两步合成 ≠ 一步重采样**。诚实地串 A→B→C 与直接 A→C 对比，27 个密度向量里 **18 个不同**
   （`two-step A->B->C differs from one-step A->C in 18 of 27 density vectors`）。两次平均再平均
   与一次重采样是两个算子，所以"组合两次搬运"即使身份全对，也不能当成一次搬运用。

## 5. 回调式 API 的写分区漏洞（issue 没问，但比较两种形状时必须报）

这是两种 API 的**真正差别**，而且与网格身份无关（`TestCallbackCanViolateWritePartition`）：

```
partition_test.go:59: callback API: row 1 was overwritten by worker 0, Finish() still passes;
field [2 999], oracle [2 3/2]
```

worker 1 先写自己的第 1 行；worker 0 拿到下标 0 后，用同一个 slice 顺手把第 1 行改成 999。
`Run` 的记账认为两行都写过、没有重复声明，`Finish()` **通过**，场是错的。生成循环形状无法表达
这个错误：循环体没有下标变量，`RowView.Store` 只写 `v.dst`（`TestWritePartitionGuards` 里断言
worker 1 跑完后第 0 行仍是 0）。

结论：**写分区只能由"生成循环 + 自身记账"强制，回调式 API 强制不了**。库可以给出行形状，但
"不要把它拆成回调"这一点，只能在代码生成或 API 设计层面保证。

## 6. 基准：plan 校验 vs 重复 apply

`go test ./xfer -run XXX -bench . -benchmem`，fixture：两个 n 单元、互相错开 1 个单位的划分
（plan 约 2n 个条目）。下表是同一批 3 次运行（`logs/bench-run1..3.txt`）的 min 与 max。

| 基准 | 单元 | ns/op (3 次 min) | ns/op (3 次 max) | B/op | allocs/op |
| --- | --- | --- | --- | --- | --- |
| `BuildPlan`（构建+校验） | 256 | 1,917,170 | 3,852,782 | 461,458 | 18,659 |
| `BuildPlan`（构建+校验） | 1024 | 8,257,161 | 33,180,815 | 1,837,966 | 74,723 |
| `Validate`（只校验已有 plan） | 256 | 1,391,171 | 3,482,259 | 368,185 | 15,589 |
| `Validate`（只校验已有 plan） | 1024 | 5,780,387 | 14,460,009 | 1,466,692 | 62,437 |
| `ApplyRows`（回调式，含 `NewRun`+`Finish`） | 256 | 575,144 | 1,592,559 | 61,952 | 3,840 |
| `ApplyRows`（回调式） | 1024 | 2,627,536 | 4,132,244 | 247,042 | 15,360 |
| `GatherRows`（生成循环式） | 256 | 467,810 | 1,074,495 | 61,760 | 3,839 |
| `GatherRows`（生成循环式） | 1024 | 2,450,224 | 3,131,479 | 246,849 | 15,359 |
| `GatherRowsW8`（8 个 worker 轮流） | 1024 | 2,058,889 | 3,745,680 | 251,902 | 15,541 |
| `ApplyUnbound`（控制：不做身份检查） | 256 | 554,637 | 679,707 | 61,696 | 3,839 |
| `ApplyUnbound`（控制） | 1024 | 2,084,356 | 2,653,845 | 246,017 | 15,359 |
| `RejectWrongMesh`（3 单元 plan 被拒一次） | 3 | 1,893 | 3,147 | 296 | 11 |
| `CheckIntegral`（事后守恒检查） | 1024 | 2,138,967 | 4,856,257 | 328,148 | 20,494 |

读数与诚实说明：

- **校验比一次 apply 贵，量级 2–4 倍，且只付一次**。同一次运行内算的比值（`logs/bench-run1..3.txt`
  逐份可核）：1024 单元是 3.50 / 1.92 / 2.20，256 单元是 2.19 / 2.18 / 2.59。`Validate` 是
  O(单元 + 条目) 的，但每一项都在 `math/big.Rat` 上做，2n ≈ 2048 个条目花 5.8–14.5 ms，
  约 2.8–7 µs/条目。它只在 plan 被**采纳**时付一次，之后按 apply 次数摊薄。
- **`BuildPlan` 是 O(n·m)**（1024² = 约 100 万次重叠判断，8.3–33 ms / 1.8 MB）。这是原型实现，
  issue 自己也指出生产实现应当走有序边归并（O(n+m)）。**我没有实现也没有测量 O(n+m) 版本。**
- **身份检查在成功路径上不花钱**：`GatherRows` 与 `ApplyUnbound` 的 allocs/op 完全相同
  （3,839 vs 3,839；15,359 vs 15,359），ns 差异在噪声内且方向不定（1024 上 min 是 unbound 更慢
  2.08 vs 2.45 ms，另一些运行里反过来）。
  被拒路径 1.9–3.1 µs 是整个调用（含 `fmt.Errorf` 拼错误串与 11 次分配），不是检查本身。
- **每行 15 次分配**（15,360/1024 = 15.0，3,840/256 = 15.0，完全稳定），约 241 B/行。这是
  `math/big.Rat` 的 Mul/Add/Set 各自分配 nat 的结果，不是我的循环；**我没有优化它**（见 §8）。
- **这台机器是共享的**：同一批三次运行里 `BuildPlan/1024` 就从 8.3 ms 漂到 33.2 ms（4×），
  `ApplyRows/1024` 从 2.63 ms 漂到 4.13 ms。所以上表并列 min/max，绝对 ns 只能当量级看；
  同一次运行内的**比值**才是可靠的（§6 第一条）。没有做统计置信区间。
- 库代码 812 行（含两个 oracle 与文档注释），测试 985 行；`go vet` 干净。

## 7. 结论：issue 那句判定条件

> 「如果普通 Go 库能绑定网格身份并在同等调用方成本下强制同样约束，就应该发库、放弃编译器特性」

**成立（drop condition holds），但有两个必须一起发布的限定。**

1. **身份、几何、守恒三条约束，普通库全部强制成功。** 网格身份是边序列的指纹（外加精确边比较
   防碰撞），绑定在不透明 `Plan` 上；权重×目标宽度 == 重叠长度、每目标单元一次写入、每源单元
   度量全部分配，三条在 `Validate` 里逐条检查并通过；组合场景里错误网格在**任何写入之前**被拒
   （H3(a) 未发生），未绑定控制则静默接受并写出"对 B 正确、对 C 错误"的场（H3(b) 未发生）。
   三条证伪条件全部未触发，H1 成立。
2. **限定一（API 形状）**：回调式 API 无法强制写分区（§5）。库能给出"生成循环 + 自身记账"的
   形状，但"别把它拆成回调"这件事无法由库在运行期保证。所以**发库时应当只发 gather-loop 形状**
   （或把回调式标记为不安全、只用于调试）。编译器特性的边际价值因此收缩为"生成这个循环形状、
   并且不生成回调形状"——是代码生成便利，不是一个库表达不了的约束。
3. **限定二（身份绑定的边界）**：库绑定的是**网格**，不是数值的来源。同一单元数的裸 `[]*big.Rat`
   从别的网格搬过来，库无从判断（`TestComposedPlanChainThroughUnion` 记录了这一点）。把身份和
   数值绑在一起需要 `Field` 类型（已实现：`ApplyFields` 会拒绝），但那要求调用方不去剥类型。
   这不是语言特性的缺口，是"值语义 + 裸 slice"的信息论限制。

一句话：**发库、放弃编译器特性；发的是 gather-loop 形状的库，并且要求场携带网格身份。**

## 8. 没做什么（明确的边界）

- **没碰 Hybrid 编译器**，没跑它、没读它、没对它的行为做任何断言；issue 也只是设计层面的主张。
- **没有浮点**：全程精确有理数，没有任何浮点误差界（issue 自己也把这条列为未做的）。
- **没有并发**：worker 轮转是顺序模拟的（`GatherRows(w, workers, ...)` 按 worker 依次调用）。
  因此对数据竞争、goroutine 调度、真实并行加速**没有任何结论**。W8 基准也只是顺序轮流。
- **只做 1D 同域、整数边**：所有 fixture 是 [0,4] 的整数划分；栅格 oracle 要求整数边。非整数边、
  不同域、2D/3D、非匹配网格一律未验证。
- **没有 O(n+m) 的生产级 planner**：`BuildPlan` 是 O(n·m)（§6 已测出代价），归并版本未实现、
  未测量。
- **没有优化 `math/big.Rat` 的 15 次分配/行**：没有做 int64 分子分母对、没有浮点快路径、没有
  profile 到具体行号。
- **指纹碰撞未实测**：设计上由精确边比较兜底（`Mesh.Same` / `bind`），但没有构造碰撞来验证。
- **没有 plan 的序列化/落盘采纳路径**：`AdmitPlan` 存在且会校验，但没有测试从磁盘读回的 plan。
- **唯一性只有结构性论证**：N4 用并查集验证 64/64 网格对的重叠图是森林，据此论证"边距唯一确定
  权重"（森林每棵树上的运输问题解唯一）。这是论证 + 结构验证，不是机械化证明，也没有做 LP。
- **没有证明 plan 的最优性**，也没有把它和 float 版实现做精度对比。
- **基准是单机共享环境的 3 次运行 min/max**，无置信区间；绝对 ns 量级会随机器负载漂移（§6）。
- **没有覆盖"两个 plan 同时写同一场"的场景**，也没做多 plan 的全局写分区检查。

## 9. 实验中途被我自己推翻的东西（诚实记录）

1. v1 的 Python 网格枚举写成 `range(len(DOMAIN)-1)`，只产出 1 个网格 → 计数断言立刻报 3 ≠ 1536。
   改成按内点集合的全部子集枚举（8 个），1536/4608 才对上。
2. 我原先断言"行内搬权重可以保持总和"（`[1/2,1/2] → [1/4,3/4]`），实测积分 6 → 9/2，**不成立**。
   原因就是后来的 N4：1D 同域下 行/列边距不独立，几何唯一确定权重，补偿扰动不存在。这条错误
   假设被删掉，换成 N4 的结构性检查。
3. 我先写了"重叠二分图是树"，实测只有 27/64 是树；正确处理是**森林**（共享边界会把问题切成
   互不相连的块，每块是一棵树，唯一性仍在块内成立）。改成无环 + 边数 == 节点数 − 连通块数后
   64/64 通过。
4. 我原以为 `CheckIntegral` 能兜住错误网格，实测 `<nil>`——因为检查按 plan 自己绑定的目标网格
   算积分，与 plan 相信同一张网格（§4 第 1 条）。这条从"证伪条件"变成了"已记录的局限"。
